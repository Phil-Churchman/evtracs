Optimising station locations

Where to put a given number of swap or charge stations so drivers travel as little as possible to reach one — solved six different ways over the scenario’s own road network.

What goes in

All three come from the scenario’s own input folder, so the stations are placed on the same network the simulation will route over. The taxi ranks stand in for demand: they are where vehicles wait between fares, and so where a battery is most likely to need swapping.

The problem being solved

This is the p-median problem. Given a fixed number of stations, choose their locations so that the total distance from every demand point to its nearest station is as small as possible. Every junction in the road network is a candidate, so on a city-sized graph there are far too many combinations to try them all.

Distance is measured along the roads, not as the crow flies. A station on the far bank of a river is close on a map and useless in practice, and only network distance tells the two apart. Before any search starts, the shortest path is computed from every rank to every node in the network, in parallel across all cores, and held in memory — every method then reads distances out of that table rather than re-routing as it goes.

That precomputation is the expensive part and it is shared, which is what makes running six methods over the same area practical.

Six ways to search one per script

  1. Interchange

    Start from a random set of stations, then try moving each one to every candidate node in turn and keep whichever single move helps most. Repeat until no move improves the total, or for 10 rounds. Exhaustive and reliably good, but it evaluates every station against every node on every round.

  2. Simulated annealing

    Move one station at a time at random, always accepting an improvement and sometimes accepting a worse solution so the search can climb back out of a dead end. The chance of doing so cools geometrically — 1500 moves at each temperature, multiplied by 0.97 each step from 1.0 down to 0.0001 — and the whole thing runs three times from different starts.

  3. Tabu search

    Sample 50 candidate moves each iteration and take the best, then forbid reversing it for the next 10 iterations so the search cannot oscillate between the same two solutions. A move that beats the best result so far is allowed through the ban anyway. Runs 100 iterations, ten times over, keeping the best.

  4. Genetic algorithm

    Hold 60 candidate solutions at once, pick parents by three-way tournament, combine them and mutate one station in five, for up to 200 generations. Explores widely because it never commits to a single line of attack.

  5. Particle swarm

    30 particles move through the space of possible station sets for 100 iterations, each pulled towards its own best solution and the swarm’s best. The quickest of the six by a wide margin.

  6. K-means and Voronoi

    The odd one out: it clusters the ranks geometrically and puts a station at each cluster centre, then draws the Voronoi catchments around them, clipped to the area boundary. It ignores the road network entirely, which makes it fast and makes its distances straight-line rather than driven — useful as a sanity check and for the catchment polygons, not as an answer.

The five network methods can be pointed at a random subset of candidate nodes with --sample N, which trades a little quality for a much shorter run on a large graph.

What comes out

swap_stations_<method>.geojson

Run with a number of stations — five if none is given — and you get the chosen locations as points, plus a line from every rank to the station it was assigned to. The lines are straight assignment links rather than routes: they show which ranks a station serves, not the path taken. The k-means run adds its Voronoi catchment polygons alongside.

facility_analysis_<method>.csv

Run with -analysis instead and the whole solve repeats for 1 to 20 stations, recording the average and worst distance to the nearest station at each count, and the total time taken. That curve is what tells you how many stations are worth building.

Two things show up. The first is that returns fall away sharply: the first five stations cut the average journey by two thirds, the next fifteen only halve it again. The second is that the thorough methods are worth their time only when the answer matters — interchange and annealing agree closely and win throughout, but take hours where the swarm takes under a minute to land within a few hundred metres of them.

K-means is shown for completeness, but its column is straight-line distance and so is not directly comparable with the rest.

Where it is used

This sits behind the Place swap stations step of the workflow. The chosen locations become the scenario’s facilities — the points agents route to when a battery runs down — and can be adjusted by hand afterwards in the facilities editor, which is where real constraints like land, grid connection and opening hours get applied.

Once a scenario has run, the station animation shows what actually happened at each of them through the day: queues, swaps and idle time. Optimised placement minimises travel to a station; it says nothing about whether that station can serve everyone who arrives. The model overview puts both in sequence.
